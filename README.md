# Histology viewer

## Описание

Histology viewer - учебный веб-сайт для работы с цифровыми гистологическими
препаратами. Он помогает студентам изучать микропрепараты в браузере,
масштабировать изображение, просматривать описание препарата и проходить
диагностические задания.

Сайт включает пользовательскую часть для просмотра материалов и прохождения
тестирования, а также административный интерфейс для управления препаратами,
диагностиками и результатами. Backend хранит данные в PostgreSQL, а frontend
построен на React и Vite.

## PostgreSQL

Backend хранит препараты, диагностики и результаты тестирования в PostgreSQL.
По умолчанию используется подключение:

```bash
postgres://postgres:postgres@127.0.0.1:5432/histology_viewer
```

Перед запуском backend поднимите PostgreSQL локально или используйте внешнюю БД.
Если параметры подключения отличаются от значения по умолчанию, задайте:

```bash
export DATABASE_URL="postgres://user:password@host:5432/database"
```

При первом старте backend создаёт таблицы и переносит данные из старых JSON-файлов
`server/data/slides.json`, `server/data/diagnostics.json`,
`server/data/diagnostic-results.json`, если соответствующие таблицы пустые.

## Авторизация админки

Административный интерфейс и все `/api/admin/*` маршруты требуют пароль. На
сервере задайте переменную окружения:

```bash
export ADMIN_PASSWORD="сложный-пароль"
```

Дополнительно можно задать постоянный секрет подписи cookie-сессий:

```bash
export ADMIN_SESSION_SECRET="длинная-случайная-строка"
```

На сервере задавайте оба значения постоянно. Если `ADMIN_SESSION_SECRET` не
задан, backend сгенерирует временный секрет при старте, и все админские сессии
будут сбрасываться после перезапуска.

Для локальной проверки можно запустить backend с временным паролем:

```bash
ADMIN_PASSWORD="test123" ADMIN_SESSION_SECRET="local-dev-secret" npm run dev
```

Если `ADMIN_PASSWORD` не задан, вход в админку будет отключён.

## Форматы препаратов

Основной формат для просмотра в браузере - DZI. Админка умеет:

- принимать готовый DZI ZIP с `.dzi` и папкой `*_files`;
- конвертировать `SVS`, `TIFF`, `NDPI`, `SCN`, `MRXS` через `vips dzsave`;
- принимать `.kfb`, но реальная конвертация зависит от серверного декодера.

Для тяжёлых и нестандартных препаратов предпочтительно заранее экспортировать
готовый DZI ZIP и загрузить его в админке. Для `MRXS` загружайте ZIP с файлом
`.mrxs` и связанной папкой данных. Для `KFB`, если `vips/OpenSlide` не
распознаёт файл, экспортируйте препарат из программы сканера в `DZI`, `TIFF`
или `SVS`, либо установите отдельный KFB-конвертер на сервер.

Ошибки конвертации сохраняются в `server/data/upload-logs`, а резервные копии
данных можно создавать и восстанавливать во вкладке `Backups` в админке.

Тяжелая конвертация `vips dzsave` выполняется отдельным Node worker-процессом.
Задачи обрабатываются последовательно: это не блокирует HTTP-сервер и не дает
нескольким большим препаратам одновременно занять память и диск.

## Запуск

В папке `server`:

```bash
npm run dev
```

Во втором терминале запустите frontend:

```bash
npm run dev -- --host 0.0.0.0
```

## Проверка состояния

Backend отдаёт диагностический endpoint:

```bash
curl http://127.0.0.1:4000/api/health
```

Если всё работает, ответ вернётся с HTTP 200 и `ok: true`. В ответе есть
состояние PostgreSQL, счётчики препаратов, диагностик, результатов, права на
папки `raw-slides`, `public/slides`, `server/data/upload-logs`, состояние
`vips/OpenSlide`, очередь worker (`conversion.worker`) и количество готовых
DZI-файлов в `public/slides`.
`adminAuth.configured` показывает, задан ли пароль администратора, а
`adminAuth.sessionSecretConfigured` - задан ли постоянный секрет cookie-сессий.

## Разработка и деплой

Код хранится в GitHub, а ветка `main` считается стабильной версией для сервера.
Изменения лучше делать в отдельных ветках и вливать в `main` через Pull Request.

Перед отправкой изменений:

```bash
npm run lint
npm run build
```

На сервере после обновления `main`:

```bash
./scripts/deploy.sh
```

Подробнее: `docs/development-workflow.md`.
